# Desain Tahap 2b — pipeline build ujung-ke-ujung tanpa AI dan tanpa UI

Iterasi 2 (revisi atas `design-review.json` iterasi 1: CHANGES_REQUESTED, 6 MEDIUM + 9 LOW; tanggapan per temuan di §16) · cabang `feat/build-pipeline` (dari `origin/main` = 4302ca9) · dokumen desain saja, belum ada kode produksi.
Semua klaim "TERBUKTI" di bawah dibaca langsung di KODE repo ini atau diukur dengan alat nyata di sandbox (apktool 3.0.3, aapt2, JDK 21); semua yang bergantung pada Docker VPS ditandai "BELUM DIUJI".

**Ringkasan.** Tahap 2b menyambungkan potongan yang sudah ada menjadi satu pipeline yang bisa dijalankan pemilik dari shell VPS tanpa AI dan tanpa UI:
`analyze` → `init` (salin baseline apktool ke `bench/<id>/project`) → ubah lewat shell bench → `diff` (hash kanonik) → `request` → `approve` (terikat hash) → worker `run_build` →
runner `apktool b` pada **snapshot** yang hash-nya dihitung ulang → signer menandatangani **salinan privat** di volume `signwork` → verifikasi (sertifikat == keystore pemilik) →
artefak bernama oleh sistem → `finish_build` → retensi → bersih. Komponen baru: `rvcore/treediff.py` (manifes/diff/salin aman), helper rantai-dirfd di `rvcore/fsutil.py` (`open_dir_chain`, `rmtree_at`, `scrub_paths`; dipakai semua konsumen `builds/` selain runner, §7.7), `rvcore/buildproto.py` (protokol runner `build`),
op `init`/`diff` di bench, tahap `build` di runner, penutupan R3/R10 di signer, `worker/builds.py` (`tasks.run_build`), `web/app/builds.py` + `python -m app.buildctl`,
dan `make verify-build`. Keputusan paling berisiko (R3/R10: runner yang memproses pohon tak tepercaya mulai bisa menulis `builds/`) diputuskan di §7 dan dibuktikan dengan tes balapan nyata.

**Tumpukan teknologi (terkunci setelah desain disetujui).** Python 3.12 stdlib saja untuk `rvcore/treediff.py`, `rvcore/buildproto.py`, `bench/workspace.py`, `runner/buildstage.py`;
Python 3.12 + dependensi web/worker yang SUDAH ada (`rq`, `redis`, `fastapi` hanya karena `app.context` diimpor) untuk `worker/builds.py`, `web/app/builds.py`, `web/app/buildctl.py`;
bash untuk `scripts/verify-build.sh`; Docker Compose v2 (berkas `docker-compose.yml`, tanpa berkas tambahan baru); alat di image TIDAK berubah pin-nya
(apktool 3.0.3 SHA-256 `dbf930b0…9423`, aapt2 `df312db8…368cc`, Build-Tools 37.0.0 `01af1793…6060`, `openjdk-21-jre-headless`). Tidak ada dependensi pip baru, tidak ada tool AI baru, tidak ada rute web baru.

## 1. Arsitektur dan alur ujung-ke-ujung

```
 pemilik (shell VPS)                                                                        TIDAK ADA jalur dari AI ke sini
   │  docker compose exec -T web python -m app.buildctl <perintah>
   ▼
 ┌───────── web ──────────────────────────────────────────────────────────────────────────────────────────────┐
 │ buildctl → builds.py → store (SQLite: build, audit)   shellspool(init|diff|run) ──► benchspool           │
 │                        jobs.enqueue_build ──► Redis/RQ ("jobs")                                          │
 └──────────────────────────────────────────────────────────────────────────────────────────────────────────┘
                                         │ RQ (tasks.run_build)                    │ spool berkas
                                         ▼                                         ▼
 ┌──────── worker (satu proses RQ) ───────────────┐                      ┌──── bench ────────────────────────────┐
 │ builds.run_build:                              │                      │ bench-daemon (tak terkurung, tanpa     │
 │ claim → runner → signer → verifikasi → nama →  │                      │ rahasia): op init → bench/<id>/project │
 │ finish → prune → bersih                        │                      │ op diff (treediff) ; op run (Landlock) │
 └──────┬────────────────────────────┬────────────┘                      │ volume: work:ro bench uploads:ro       │
        │ spool (a<id>-build-…)      │ signspool (g<id>-<bid>-…)         └───────────────────────────────────────┘
        ▼                            ▼
 ┌──── runner (tanpa jaringan) ───┐  ┌──── signer (tanpa jaringan, keystore) ──────────────────────────────────┐
 │ stage build:                   │  │ buka builds/<a>/<b>/unsigned.apk SEKALI → salin ke signwork/<job>/in.apk │
 │ bench/<a>/project (ro) → copy_ │  │ zipalign → apksigner sign → apksigner verify (SEMUA di signwork privat)   │
 │ tree_safe → builds/<a>/<b>/src │  │ cert == keystore pemilik → terbitkan signed.apk ke builds (O_EXCL+rename) │
 │ hitung ulang diff_sha256 ≠ →   │  │ baca ulang & cocokkan hash                                               │
 │ workspace_changed ; sama →     │  └───────────────────────────────────────────────────────────────────────────┘
 │ apktool b -f → unsigned.apk    │
 └────────────────────────────────┘          volume `builds`: runner rw · signer rw · worker rw · web rw (hapus)
                                             volume `signwork`: signer SAJA · volume `bench`: runner ro (BARU)
```

**Alur satu build normal** (nomor = urutan waktu; huruf kecil = aktor):
1. web: `analyze` → upload/dedup lewat fungsi yang ada (APK dialirkan lewat stdin: `analyze -`) → RQ `run_analysis` → worker+runner → analisis `done`.
2. web→bench: `init` (op baru) → `bench/<id>/project/` = salinan `work/<id>/apktool`. AI/pemilik mengubah `project/` lewat `shell` (`buildctl shell` = `shellspool.run_command` langsung: jalur bench + Landlock yang sama dengan `shell_run`, tanpa `ai.tools` dan tanpa syarat `AI_SHELL_ENABLED`).
3. web→bench: `diff` (op baru) → `diff_sha256` + ringkasan. web: `request` → `store.create_build` (`awaiting_approval`, hash + ringkasan ≤ 8192 karakter).
4. web: `approve --diff-sha256 H` → `store.approve_build` (CAS terikat hash) → `queue_build` → RQ `tasks.run_build(build_id)`.
5. worker: cek signer hidup+keystore ok → `claim_build` → buat folder build → kirim job `build` ke runner → tunggu (batas waktu, pembatalan).
6. runner: snapshot → hitung ulang hash (beda = `workspace_changed`, tidak build) → tambah berkas jejak → `apktool b -f` → `unsigned.apk` → hasil dinormalkan.
7. worker: `mark_signing` → kirim job `sign` (klien `rvcore/signspool`) → signer bekerja di `signwork` → hasil.
8. worker: verifikasi hasil (ok, sertifikat == pemilik, v2+v3, 1 penanda tangan, `input_sha256 == output_sha256` runner) → baca ulang `signed.apk` dari fd dan cocokkan hash → ganti nama ke nama turunan sistem → `finish_build(verify_ok=1)` → prune → bersihkan sisa.

**Konsekuensi satu runner dan satu worker.** Build ikut antre FIFO global RQ (`jobs`) di belakang analisis yang sudah masuk, lalu menunggu runner bebas; tiap job runner diikuti daur ulang kontainer (keluar setelah uptime ≥ 12 dtk, lalu Docker memulai ulang) sehingga
setiap build menambah jeda dasar yang kira-kira belasan detik di luar waktu alat (perkiraan dari kode, BELUM DIUKUR di Docker). Analisis APK besar (sampai `JOB_TIMEOUT` 2700 dtk) menahan build di belakangnya, dan sebuah build menahan analisis berikutnya selama `TIMEOUT_BUILD`+`TIMEOUT_SIGN` paling lama.
Ini sesuai keputusan pemilik #6 ("build & analisis diserialkan di runner"); tidak ada paralelisme yang hilang karena runner memang satu job sekali jalan. `status` menampilkan posisi antrean RQ dan alasan menunggu (§9).

### 2.2 State machine dan penulisnya

Tabel transisi TIDAK berubah (`store.BUILD_TRANSITIONS`, sumber kebenaran tunggal; semua perubahan lewat CAS). 2b hanya menambah **pemanggil**:

| Transisi | Penulis (proses) | Fungsi store |
|---|---|---|
| ∅ → `awaiting_approval` | web (`builds.request_build`) | `create_build` |
| `awaiting_approval` → `approved` | web (`builds.approve_build`, via=cli) | `approve_build` (terikat hash; satu-satunya jalan) |
| `approved` → `queued` | web (setelah approve), worker (`requeue_orphans`) | `queue_build` |
| `queued` → `building` | worker | `claim_build` |
| `building` → `signing` | worker | `mark_signing` |
| `signing` → `done` | worker | `finish_build` (`verify_ok=1` wajib) |
| `approved\|queued\|building\|signing` → `failed` | worker; `recover_stuck_builds` untuk `building\|signing` | `fail_build` / `recover_stuck_builds` |
| `awaiting_approval\|approved\|queued` → `cancelled` | web (`cancel`) | `request_cancel_build` |
| `building\|signing` → `cancelled` | worker (setelah `cancel_requested=1`) | `cancel_build` |
| final → dihapus | worker (prune), web (hapus analisis, CASCADE) | `delete_build`, `delete_apk` |

`rejected` tidak punya perintah CLI di 2b (`cancel` dari `awaiting_approval` cukup); `reject_build` tetap ada untuk Tahap 5.

| Jalur | Penulis | Pembaca | Masa hidup |

Invarian yang dijaga SATU tes tabel (`tests/test_build_compose.py`, tanpa PyYAML; deep-merge hanya bila PyYAML ada), bukan lagi tes terpisah-terpisah:
1. Himpunan pemasang dan mode tiap volume PERSIS sama dengan tabel (volume baru atau pemasang ekstra = gagal).
2. runner: `bench` HANYA `:ro`, `builds` rw, **tanpa** `benchspool`/`signspool`/`signwork`/`files`/`db`, tanpa `secrets:`, tanpa `docker.sock`; `network_mode: none`, `read_only`, `user 10001`, `cap_drop ALL`, `no-new-privileges`, `mem_limit 3g`, `cpus 2`, `pids_limit 512` tidak berubah.
3. bench: tanpa `builds`/`signwork`/`signspool`; `signwork` hanya `signer`; `signspool` hanya `worker`+`signer`.
4. tmpfs: satu-satunya `exec` di seluruh compose tetap `/opt/aapt-exec` milik runner (16m, `uid=10001`); `/tmp` runner tetap `rw,size=256m,nosuid` tanpa `exec`; tidak ada tmpfs baru.

## 4. Protokol op baru `init` dan `diff` (bench) dan ruang kerja `$WS` vs `$WS/project`

### 4.1 Kontrak ruang kerja (menyelaraskan "awalnya kosong" dengan `init`)
- `$WS` = `/data/bench/<aid>` (tetap; `policy.workspace`). Tool `shell_run` dan Landlock **tidak berubah**: kurungan memberi `RW` pada seluruh `$WS` (`policy.rules_for`: `Rule(workspace, RW)`), jadi tulis di `$WS/project/...` sudah diizinkan; tes baru membuktikannya dari aturan, bukan dari asumsi.
- **Pohon yang dibangun dan di-diff adalah `$WS/project`, hanya itu.** Berkas lain di `$WS` (catatan, skrip) bebas dan diabaikan sistem. Sebelum `init`, `project/` tidak ada dan `diff`/`request` ditolak (`kode=belum_init`).
- `$WS` dibuat mode 0700 oleh daemon (op `init` atau `run` pertama). Teks deskripsi tool AI ("`$WS` ... mengubah salinan smali di `$WS`") TIDAK diubah di 2b (larangan menyentuh `ai/tools.py`); Tahap 4 memperbarui teks dan memanggil `init`.
- Path dihitung bench dari `analysis_id` (int `1 ≤ n ≤ MAX_PROTO_ID = 999_999_999`, D13) saja: `policy.project_dir(dirs, aid) = dirs.bench/<aid>/project`, `policy.base_tree(dirs, aid) = dirs.work/<aid>/apktool`. Tidak ada path, nama, atau sha256 dari web yang dipakai op baru.

### 4.2 Permintaan (web → bench, `rvcore/shellspool.py`)

| Bidang | `init` | `diff` | Aturan validasi (di `bench-daemon.validate_*`, DI SISI PENERIMA) |
|---|---|---|---|
| `job_id` | `s<aid>-<hex12>` | sama | regex `JOB_ID_RE` yang ada; tak cocok → dibuang `Spool` |
| `op` | `"init"` | `"diff"` | bukan salah satu `{run, init, diff}` → hasil `refused` "operasi tidak dikenal" (perilaku lama untuk op lain dipertahankan) |
| `analysis_id` | int | int | `type is int`, bukan bool, `1 ≤ n ≤ 999_999_999` (job id bench `s<aid>-…` hanya 9 digit; D13); selain itu `refused` |
| `force` | bool | – | **harus `type is bool`**; selain itu `refused`. Default pembuat permintaan `False` |
| `timeout` | int | int | int ≥ 1 (bukan bool), dijepit ke `OP_MAX_TIMEOUT = 600` dtk — batas sendiri, bukan `BENCH_CMD_MAX_TIMEOUT` (hash pohon besar lebih lama dari perintah shell 120 dtk) |
| bidang lain (`path`, `command`, `sha256`, …) | diabaikan | diabaikan | tak pernah dibaca |

`shellspool` bertambah: `OP_INIT`, `OP_DIFF`, `build_init_request`, `build_diff_request`, `parse_init_result`, `parse_diff_result`, `run_op` (inti tunggu-hasil dari `run_command` dipakai bersama: heartbeat, `pickup_timeout`, pembatalan, `grace`; `run_command` dipertahankan dengan perilaku sama). `read_result` menerima `parser=` (bawaan `parse_result`). Batas 1 MB hasil dan `read` berbatas tidak berubah. Untuk op baru `pickup_timeout` 120 dtk (bukan 30): bench mungkin sedang menjalankan perintah AI sampai 120 dtk.

### 4.3 Hasil dan normalisasi sisi web (hasil bench TIDAK tepercaya)
- `init` → `{status: ok|refused|failed|timeout|cancelled, created: bool, reason: created|exists|reset, files, dirs, bytes (int ≥ 0), skipped: {symlink, special, root_ignored} (int ≥ 0), message ≤ 600}`. `parse_init_result` memaksa tipe, memotong teks, membuang bidang tak dikenal; `status` di luar daftar → `failed`; JSON rusak/besar → `failed` ("hasil bench rusak").
- `diff` → `{status, diff_sha256 (hex64 atau ""), counts: {added, modified, removed}, entries_total, base_entries, bytes: {added, modified, removed}, kinds: {smali, res, manifest, aset, lib, lain: int}, lines: {plus, minus, files, skipped_files}, skipped: {symlink, special, root_ignored, vanished}, top: [≤ 40 × {op: A|M|R, kind: f|d, path ≤ 300, size, plus|null, minus|null}], truncated: bool, message}`. `parse_diff_result`: `diff_sha256` harus `[0-9a-f]{64}` (selain itu → `status=failed`), semua angka int 0..2**50, `top` dipotong 40, `path` hanya karakter cetak tanpa pengendali arah (nama berkas buatan AI bisa memuat `\n` untuk memalsukan keluaran CLI).
- Ringkasan untuk `diff_summary` store dibangun web dari hasil ini: `{"v":1,"counts":…,"bytes":…,"kinds":…,"lines":…,"skipped":…,"top":[…],"truncated":…}`; `builds.py` memperkecil dengan langkah TETAP: bila `len(json.dumps(..., sort_keys=True, ensure_ascii=False)) > 7000` maka `top` dipotong separuh (40→20→10→5→2→1→0) dan `truncated=true`, diulang sampai ≤ 7000. Batas store 8192 karakter MENOLAK (tidak memotong; `create_build` + `CHECK length(diff_summary) <= 8192`), sisa 1192 untuk pembungkus. `top` sudah kosong tetapi masih > 7000 → `BuildsError('ringkasan_terlalu_besar')` (tidak mungkin terjadi: semua bidang lain bertipe/berukuran tetap; tes memakai 40 × `path` 300 karakter).
- Potongan diff teks per berkas untuk Tahap 5: **TIDAK dikerjakan** (brief: tidak wajib). Hanya `top` + ukuran/hitung baris.

### 4.4 Semantik `init` dan keputusan `force` (DIPILIH: pemilik/CLI saja, tidak pernah AI)
- Tanpa `force`: bila `project` sudah ada (direktori, symlink, atau berkas) → `ok, created=false, reason=exists`, **nol perubahan** (tidak ada pekerjaan AI yang tertimpa; idempoten, jadi `init` dua kali aman).
  `message` hasilnya tegas: "project sudah ada; isinya TIDAK dibandingkan dengan baseline (lihat `diff`; `init --force` mengulang dari baseline)". Kasus nyata: AI melakukan `mkdir project` sebelum `init`; `diff` lalu memberi `peringatan=baseline_tidak_utuh` (§4.5).
- `force=true` → `reason=reset`: salin baseline ke `.project.tmp` DULU (galat → `project` lama utuh), baru `project` lama dihapus tanpa mengikuti symlink (`safe_rmtree`/`unlink`) dan `.project.tmp` di-`rename` ke `project`. Jendela antara hapus dan rename hanya kehilangan `project` (bukan data lain); `init` ulang memulihkan. `.project.tmp` sisa (daemon mati) dihapus di awal `init` berikutnya dan ikut hilang saat ruang kerja dihapus.
- Siapa yang bisa memanggil `force`: HANYA `buildctl init --force` (shell VPS pemilik) lewat `shellspool.run_op`. Tidak ada tool AI yang membangun permintaan `init` (tool AI tidak disentuh); bench tidak mempercayai web untuk hal lain, tetapi `force` memang sah dari web — pembatasnya adalah tidak adanya pemanggil AI, dijaga tes statis (§12.3 G-AI).
- Prasyarat: `work/<aid>/apktool` direktori nyata (bukan symlink) berisi `AndroidManifest.xml` berkas biasa; selain itu `refused` kode `baseline_tidak_ada`.
- Penyalinan: `treediff.copy_tree_safe(base, ws/.project.tmp, Limits(max_total_bytes = ¾ kuota ruang kerja))`, lalu `rename(.project.tmp, project)`, `on_tick` menulis detak "busy", mengecek pembatalan dan tenggat. **Pasca-salin**: `executor.tree_bytes(ws)` (blok disk, ukuran yang dipakai kuota `run`) harus ≤ 90% `BENCH_WORKSPACE_MAX_MB`; bila tidak, `project` dibatalkan dan `refused` kode `kuota` — jaminan: `init` yang sukses tidak membuat perintah shell pertama ditolak karena kuota.
- `executor.touch_activity(ws)` dipanggil di awal dan akhir (penanda `.last-used`; penyapu yatim `sweep_orphan_workspaces` tidak berubah).
- Kegagalan: `OSError` saat menyalin → `failed` + pesan tanpa path (`type(exc).__name__`/errno), `.project.tmp` dihapus, log `say()` satu baris; `TreeLimitError` → `refused` dengan kode batas; daemon tidak mati.

### 4.5 Semantik `diff`
`treediff.compute_diff(base_tree, project, Limits(), on_tick)` atas pohon HIDUP. Karena bench menjalankan SATU job sekali dan semua proses latar perintah dibunuh setelah tiap perintah (`reap_descendants`), tidak ada penulis AI yang berjalan selama `diff` di bench: hasilnya konsisten. (Runner, yang membaca pohon yang sama dari kontainer lain, TIDAK punya jaminan itu — karena itu runner menyalin snapshot dan menghitung ulang, §6.) `project` tidak ada → `refused` `belum_init`. Hasil `diff` kosong (0 perubahan) sah dan hash-nya tetap (hash dari payload `e=[]` dengan `base` yang sama). Hasil memuat `base_entries`; bila `base_entries > 0` dan `removed·10 ≥ base_entries·9`, CLI (`diff`/`request`) mencetak `peringatan=baseline_tidak_utuh` (project hampir kosong/bukan salinan baseline; build TIDAK diblokir, pemilik diberi tahu).

## 5. `rvcore/treediff.py` (stdlib saja)

### 5.1 API
```
Limits(max_entries=600_000, max_total_bytes=3 GiB, max_file_bytes=1 GiB, max_depth=64, max_name_bytes=255, max_path_bytes=1024)
ROOT_IGNORE = ("build", "dist")                  # hanya di AKAR pohon, peka huruf besar-kecil
class TreeLimitError(Exception): code in {too_many_entries, too_large, file_too_large, too_deep, name_too_long, unreadable, timeout, cancelled}
compute_diff(base, work, limits=Limits(), *, on_tick=None, text_stats=True) -> DiffResult
copy_tree_safe(src, dst, limits=Limits(), *, on_tick=None) -> CopyStats
manifest_hash(root, limits)   # digest manifes satu pohon (= `base` di payload hash, §5.3; alat uji)
```
Tidak ada impor di luar stdlib. `on_tick()` dipanggil tiap 1000 entri atau 64 MiB dan boleh melempar `TreeLimitError('cancelled'|'timeout')` (bench/runner menyuntikkan pemeriksaan pembatalan, tenggat, dan detak jantung).

### 5.2 Manifes kanonik (satu pejalan untuk bench, runner, dan salin)
- **Pejalan aman**: akar dibuka `os.open(root, O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC)`; setiap subdirektori dibuka relatif `dir_fd` dengan `O_NOFOLLOW|O_DIRECTORY`; entri dienumerasi `os.scandir(fd)` dan di-`stat(name, dir_fd=, follow_symlinks=False)`. Berkas dibuka `O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC` lalu `fstat` HARUS `S_ISREG` sebelum dibaca (FIFO yang ditukar di antara `lstat` dan `open` tidak menggantung; pola `signkeys.OPEN_FLAGS`). Symlink tidak pernah diikuti, di tingkat mana pun (AI menulis di pohon ini).
- **Urutan kanonik dan kunci banding (SATU definisi untuk pejalan, penggabung, dan pembangkit hash)**: `key(path) = tuple(os.fsencode(c) for c in path.split('/'))` — komponen sebagai BYTE, bukan string path penuh. Pejalan = DFS yang mengurutkan nama dalam tiap direktori menurut byte; urutan itu IDENTIK dengan urutan leksikografis `key()`. Ini BUKAN urutan string path penuh karena `/` (0x2F) lebih besar daripada `-` (0x2D) dan `.` (0x2E): pada DFS `res/values/x.xml` mendahului `res/values-v21/y.xml`, kebalikan dari urutan string (pasangan `values`/`values-v21`, `layout`/`layout-land` ada di hampir setiap pohon apktool). Penggabung §5.3 WAJIB membandingkan `key(a)` dengan `key(b)`, tidak pernah string path. `A.txt` dan `a.txt` adalah dua entri berbeda (peka huruf besar-kecil, tanpa normalisasi Unicode). Urutan `scandir`, nomor inode, dan mtime tidak berpengaruh.
- **Entri**: berkas biasa → `(path, 'f', size, sha256(isi), x)` dengan `x = 1` bila ada bit eksekusi apa pun, selain itu 0 (mode lain, pemilik, mtime diabaikan). Direktori → dicatat **hanya bila kosong** (`(path, 'd')`; direktori berisi tercermin lewat berkasnya). `size` dan `sha256` adalah byte yang BENAR-BENAR terbaca (berkas yang tumbuh saat dibaca tetap konsisten; dibatasi `max_file_bytes`).
- **Entri khusus** (aturan terdokumentasi, ditegakkan di pejalan): symlink, perangkat, FIFO, soket → **DIABAIKAN dan DIHITUNG** (`skipped.symlink`, `skipped.special`), tidak masuk hash. Konsisten dengan build: `copy_tree_safe` membuang entri yang sama, jadi pohon yang dibangun == pohon yang di-hash. Entri yang hilang di tengah jalan (`ENOENT`) dilewati dan dihitung (`vanished`); `EACCES`/`EPERM` pada berkas/direktori → `TreeLimitError('unreadable')` dengan path RELATIF (pohon proyek; aman ditampilkan) — gagal-tertutup, bukan diam-diam menghilangkan berkas.
- **Pengecualian akar**: `build/` dan `dist/` DI AKAR dilewati di kedua pohon dan dihitung (`root_ignored`). Alasan keamanan di §0 D1 (cache dex `apktool b`). Nama itu di kedalaman lain TIDAK dikecualikan.
- **Batas** (zip-bomb jujur; semuanya `TreeLimitError`, tidak pernah memotong diam-diam): jumlah entri, total byte isi, byte per berkas, kedalaman, panjang nama (byte UTF-8, 255 = `NAME_MAX`), panjang path relatif (1024 byte). Nilai bawaan sama untuk bench dan runner (konstanta, bukan env) sehingga keputusan "terlalu besar" identik di kedua sisi; `MAX_OUTPUT_MB` dsb. tidak memengaruhinya.
- **Rekursi**: kedalaman pejalan ≤ `max_depth` (64) — jauh di bawah batas rekursi Python; `RecursionError` apa pun ditangkap pembungkus publik dan dijadikan `TreeLimitError('too_deep')`.

### 5.3 Diff dan `diff_sha256` kanonik
- Gabungan-urut (merge) dua aliran manifes (dasar dan kerja) berdasarkan `key(path)` menghasilkan aliran entri diff TANPA menyimpan seluruh manifes di memori (600.000 entri × 2 akan memakan ratusan MB di bench 1g): `key` dasar < `key` kerja → `R` (hanya di dasar); `key` kerja < `key` dasar → `A` (hanya di kerja); `key` sama dan keduanya berkas → `M` bila `sha256` atau `x` beda; `key` sama tetapi jenis beda (berkas ↔ direktori kosong) → `R` lalu `A`. Berkas `a` (key `(a,)`) ↔ direktori berisi `a/b` (key `(a,b)`) jatuh sebagai `R a` lalu `A a/b` tanpa kasus khusus.
- Bentuk entri (daftar, urutan bidang tetap): `A`/`R`: `[op, path, kind, size, sha256|"", x]` (`R` mendeskripsikan entri LAMA); `M`: `[op, path, "f", new_size, new_sha, new_x, old_size, old_sha, old_x]` (mengikat versi basis juga).
- `diff_sha256 = sha256( json.dumps({"v":2,"base":"<hex64>","e":[entri…]}, separators=(",",":"), ensure_ascii=True) )`, dihitung **streaming** dari potongan byte yang identik dengan hasil `json.dumps` penuh (tes membandingkan keduanya pada pohon kecil). `ensure_ascii=True` membuat nama non-UTF-8 (`surrogateescape`) tetap terserialisasi deterministik. Isi di-hash, bukan teks diff; baris +/− TIDAK ikut hash. **`base` = `base_sha256`** = SHA-256 berjalan atas rekaman manifes DASAR dalam urutan kanonik (tiap entri dasar: `json.dumps([path, kind, size, sha256|"", x], separators=(",",":"), ensure_ascii=True) + "\n"`; `build/`/`dist/` akar tidak termasuk), dihitung dari aliran dasar yang SUDAH dibaca penggabung (nol I/O tambahan, nol manifes di memori). Alasan (review F-01): runner memasang `work` rw dan memproses APK hostile; hash hanya-delta tidak mengikat dasar, jadi dasar `work/<aid>/apktool` yang diubah antara `request` dan snapshot lolos dengan hash sama. Dengan `base`, hash mengikat (dasar + delta) = SELURUH isi pohon yang dibangun, sehingga klaim "snapshot == yang disetujui" benar (batasnya di §6.2 langkah 4). Versi payload 2 adalah satu-satunya yang pernah ada (2b rilis pertamanya; tidak ada hash `v:1` tersimpan).
- Properti yang dijaga tes (acak berbiji, bukan hipotesis library): urutan pembuatan berkas, inode, mtime, mode selain bit x, dan urutan `scandir` tidak mengubah hash; satu byte beda, satu bit x beda, satu berkas lebih/kurang, atau satu direktori kosong lebih mengubah hash; **mengubah SATU berkas DASAR yang tidak ada di diff (pohon kerja tetap) mengubah hash** (F-01); `A.txt`/`a.txt`; nama Unicode (NFC vs NFD sebagai dua berkas); nama 255 byte lolos, 256 `name_too_long`; pohon dengan 600.001 entri (batas diturunkan di tes) ditolak; symlink/FIFO/soket diabaikan dan dihitung; FIFO bernama `x` tidak menggantung (dibatasi `within(5)`).
- **Tes urutan banding (F-02)**: dasar memuat `res/values/strings.xml` dan `res/values-v21/styles.xml` (juga `res/layout/a.xml` + `res/layout-land/a.xml`); hapus yang pertama → hasil TEPAT satu `R` (tanpa `A` palsu); ubah yang kedua → TEPAT satu `M`; tambah `res/values/new.xml` → TEPAT satu `A`; urutan entri di JSON = urutan DFS yang sama. Dijalankan pada generator acak yang menyisipkan nama dengan `-`, `.`, spasi, dan awalan bersama.
- Hash pohon yang sama dari bench (hidup) dan runner (snapshot hasil `copy_tree_safe`) **harus identik** untuk isi yang sama — tes lintas: bangun pohon, `compute_diff(base, work)`, `copy_tree_safe(work, snap)`, `compute_diff(base, snap)` → hash sama, termasuk saat `work` berisi symlink/FIFO/`build/`.

### 5.4 Ringkasan (`DiffResult`) dan batasnya
`counts`, `entries_total`, `base_entries` (jumlah entri manifes dasar), `bytes` (jumlah ukuran baru untuk A/M, ukuran lama untuk R), `kinds` (jenis dari komponen pertama path: `smali*` → smali; `res` → res; `AndroidManifest.xml` → manifest; `assets` → aset; `lib` → lib; lainnya → lain), `skipped`, `top` (40 entri berubah terbesar menurut `|Δ ukuran|`, seri diputus menurut path), `truncated` (ada lebih dari 40).
Baris +/−: hanya untuk berkas yang tampak teks (8 KiB pertama tanpa NUL) dan kedua sisinya ≤ 256 KiB, maksimum 300 berkas pertama (urutan kanonik); sisanya dihitung `lines.skipped_files`. Dihitung dengan selisih multiset baris (`Counter`), O(n): **perkiraan** (baris yang hanya pindah tidak terhitung), bukan diff Myers — cukup untuk ringkasan, dan sengaja di luar hash.
**NB-1**: (1) `treediff` hanya menghasilkan struktur datar berkedalaman tetap; (2) `store.create_build` menangkap `RecursionError` di samping `(TypeError, ValueError)` → `BuildInputError` (pemilik invarian "ringkasan harus bisa diserialisasi" adalah store); (3) `builds.request_build` memverifikasi kedalaman ≤ 4 sebelum memanggil store. Tes: struktur 100.000 tingkat → `BuildInputError`, bukan `RecursionError`.

### 5.5 `copy_tree_safe(src, dst, limits, on_tick)`
Membuat `dst` dengan `mkdir` eksklusif (sudah ada → `FileExistsError` ke pemanggil; pemanggil yang memutuskan) mode 0755, lalu menyalin lewat pejalan aman yang sama: direktori dibuat 0755 (hanya yang berisi atau kosong sesuai manifes), berkas dibuat `O_CREAT|O_EXCL|O_NOFOLLOW` mode **0644 atau 0755** menurut bit x (mode deterministik; tidak ada mode 000/444 yang menyulitkan penghapusan oleh uid lain), isi disalin dari fd yang sudah divalidasi `S_ISREG`, mtime tidak dipertahankan. Symlink/perangkat/FIFO/soket dan `build/`/`dist/` akar tidak disalin. Mengembalikan `CopyStats(files, dirs, bytes, skipped_symlink, skipped_special, root_ignored, vanished)`. Galat di tengah → `dst` setengah jadi DIBIARKAN untuk pemanggil, yang wajib menghapusnya (`safe_rmtree`): `init` memakai `dst = .project.tmp` lalu `rename` ke `project` (jadi `project` tidak pernah setengah jadi); runner memakai `build_dir/src` dan membersihkannya di `finally`.

Beda → hasil `workspace_changed` (teks: "Ruang kerja atau baseline berubah setelah build diajukan (hash diff tidak sama); ajukan build baru.") — termasuk bila yang berubah adalah DASAR (F-01) —, `src/` dihapus, **apktool tidak dijalankan**. Sama → isi `src/` == dasar + delta yang disetujui (kecuali berkas jejak, langkah 5). Yang TIDAK dibuktikan: keluaran kompilator, dan perubahan `src/` oleh proses runner lain SESUDAH hash dan sebelum apktool membaca (satu domain kepercayaan, uid sama; R-2).
5. **Jejak FR-9.23**: tulis `src/assets/reverse-apk-modified.txt` (`mkdir assets` bila perlu; `O_NOFOLLOW`, `unlink` dulu; berkas bernama sama milik AI ditimpa — "ditambahkan sistem, bukan AI") berisi 5 baris tetap: pernyataan "APK ini HASIL MODIFIKASI", `asal_sha256=`, `diff_sha256=`, `build=<bid>`, `waktu_utc=`. Env minimal seperti stage lain (`HOME=/tmp/home/<job>` di tmpfs `/tmp`; `JADX_OPTS` tidak dipakai). Pada pemakaian pertama apktool memasang `framework/1.apk` ke `$HOME/.local/share/apktool/framework` dari jar (diukur di sandbox: `d`/`b` berhasil dengan HOME segar tanpa jaringan; beberapa MiB di `/tmp` 256m — BELUM DIUJI di tmpfs Docker). Proses di grup sendiri (`start_new_session`).
7. **Pengawasan** (loop kecil milik `runner/buildstage.py`; `_run_tool` dan stage lama TIDAK diubah sama sekali — tidak ada ekstraksi `_watch`, F-11; satu tes membandingkan perilaku kedua loop pada kasus timeout/pembatalan yang sama): detak jantung tiap 5 dtk; `cancel_requested(job_id)` → `cancelled`; `STOP` → `aborted`; lewat `timeout` → `timeout`; tiap 5 dtk ukur KELUARAN saja: `tree_stats(src/build, MAX_OUTPUT_BYTES, MAX_OUTPUT_FILES)` + ukuran `unsigned.apk` (`fstatat`). Melebihi → `output_limit`; semua mematikan SELURUH grup (`kill_group`).

  4. karakter kontrol dan pengendali arah dibuang.
  Path PROYEK relatif (`res/…`, `smali/…`) sengaja dipertahankan (bukan rahasia; dibutuhkan AI untuk memperbaiki). Tes tabel (masukan → keluaran) untuk: `smali/com/x/work/Foo` utuh, `work/12/apktool/x` → `<path>`, `>/data/work/1` → `><path>`, `<proyek>/lib/x.so` utuh, `/data/builds/3/7/src/res/values/strings.xml` → `<proyek>/res/values/strings.xml`, `/data/builds/3/7/unsigned.apk` → `<build>/unsigned.apk`.

## 7. KEPUTUSAN R3/R10 — TOCTOU "oracle penandatanganan" (WAJIB sebelum runner menulis `builds/`)

### 7.1 Masalah, dibuktikan di kode 2a (`signer-daemon._process`)
Semua kontainer memakai uid 10001, jadi izin berkas tidak memisahkan runner dari signer. Signer 2a membuka `unsigned.apk` SEKALI hanya untuk memeriksa ukuran lalu **menutup fd** (`os.close(fd)` setelah `open_input`), dan sesudah itu `zipalign`/`apksigner` membuka `bdir/unsigned.apk`, `.sign-aligned.tmp`, `.sign-signed.tmp` lewat **jalur string** di folder yang kini bisa ditulis runner. Pelaku yang bisa menulis folder itu (runner yang memproses pohon hostile; atau job runner berikutnya) dapat: (a) menukar `unsigned.apk` setelah pemeriksaan sehingga signer menandatangani byte lain; (b) menukar `.sign-signed.tmp` SETELAH `apksigner verify` lulus sehingga `sha256_fd` + `os.replace` menerbitkan berkas yang tak pernah diverifikasi dengan `ok:true` dan `cert_sha256` pemilik; (c) menanam symlink/FIFO/direktori pada nama keluaran.

### 7.2 Keputusan: **kerja privat di volume `signwork` + salin-sekali dari fd + rantai hash + terbit tahan balapan**
Signer hanya mengerjakan byte yang ia salin sendiri dari satu fd ke tempat yang TIDAK terjangkau runner. Urutan baru `_process` (menggantikan langkah 5.2 2a; yang tidak disebut tidak berubah):
1. `bfd = open_build_dir(aid, bid)` (rantai `O_DIRECTORY|O_NOFOLLOW` — perilaku tetap; fungsi di skrip signer menjadi pembungkus tipis `fsutil.open_dir_chain` yang memetakan `OSError` ke `JobError` seperti 2a, jadi tes 2a tidak berubah; §7.7); `sweep_leftovers(bfd)` (hapus `signed.apk`, `.sign-*`, `*.idsig` sisa; tetap, sebelum cek disk). `wfd` = fd `signwork` (dibuka `O_NOFOLLOW|O_DIRECTORY`); `wdir = signwork/<job_id>` dibuat `mkdir` mode 0700 **eksklusif** relatif `wfd` (ada → `safe_rmtree` dulu; id job unik sehingga jarang).
2. `fd, size = open_input(bfd, "unsigned.apk", SIGN_MAX_MB)` (`OPEN_FLAGS` = `O_NOFOLLOW|O_NONBLOCK`; `S_ISREG`; `nlink == 1`; `0 < size ≤ max`) — **fd ini TIDAK ditutup sampai penyalinan selesai**.
3. **Cek disk dua volume** (sebelum menyalin; `check_disk` yang ada): `signwork` butuh `2 × size + 16 MiB + 1 GiB` (puncak: `in` + `aligned`, lalu `aligned` + `signed`, karena `in.apk` dihapus setelah `zipalign`); `builds` butuh `size + 16 MiB + 1 GiB` (salinan terbit). Kurang → `no_space`.
4. **Salin dari fd yang sama** ke `wdir/in.apk` (`O_CREAT|O_EXCL|O_NOFOLLOW`, 0600) sambil menghitung SHA-256: membaca paling banyak `max + 1` byte; berkas yang tumbuh melewati `max` → `input_too_large`; `on_tick` tiap 64 MiB (detak jantung/pembatalan). Hasilnya `input_sha256` dan `input_size` = byte yang SUNGGUH disalin. Tutup `fd`. Sejak titik ini `builds/…/unsigned.apk` tidak pernah dibaca lagi.
5. `zipalign -P 16 -f 4 in.apk aligned.apk` lalu `zipalign -c`; `in.apk` dihapus. `apksigner sign` (flag 2a tidak berubah; kata sandi tetap hanya `--ks-pass file:`) `aligned.apk → signed.apk`; `aligned.apk` dihapus; `apksigner verify --verbose --print-certs signed.apk`; `evaluate_verify` (rc 0, v2 dan v3, tepat satu penanda tangan, SEMUA digest == sidik jari pemilik). **Semua path alat berada di `wdir` yang hanya signer yang bisa menulis.**
6. Identitas berkas terverifikasi: buka `wdir/signed.apk` (`OPEN_FLAGS`), `fstat` reguler, `sha256_fd` → `sha`, `size` (tak ada balapan: folder privat; tetap `fstat`).
7. **Terbit tahan balapan** ke folder build (runner-writable): `out = os.open(".sign-signed.tmp", O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC, 0o644, dir_fd=bfd)` (nama sudah ada — dari penyerang — berarti `EEXIST` → gagal-tertutup `internal`, bukan menimpa/mengikuti); salin dari fd langkah 6 (`lseek(0)`) sambil menghitung hash (harus == `sha`); `fsync`; `os.replace(".sign-signed.tmp", "signed.apk", src_dir_fd=bfd, dst_dir_fd=bfd)` (`rename` mengganti entri direktori, tidak mengikuti symlink; target direktori berisi → galat → `internal`).
8. **Baca ulang** (deteksi tukar dalam jendela signer): `os.open("signed.apk", OPEN_FLAGS, dir_fd=bfd)`, `fstat` reguler + `nlink == 1` + ukuran, `sha256_fd` == `sha`. Beda → `unlink` + `JobError('internal', 'keluaran berubah saat diterbitkan')`.
9. Hasil `ok:true` memuat `input_sha256` (baru), `output_sha256 = sha`, `cert_sha256`, `verify`, `signer_count`. `cleanup_job_files` + `safe_rmtree(wdir)` SEBELUM `Spool.finish` (adendum 2a butir 5 tetap).
Signer start: `abort_orphans` juga `safe_rmtree` seluruh isi `signwork` (hanya signer yang memakainya; tak ada job berjalan saat start). `signspool.parse_result`: `input_sha256` (hex64) ikut syarat koheren `ok`; `ERROR_CODES` tidak bertambah (`internal`, `input_unsafe`, `input_too_large`, `no_space` cukup).

### 7.3 Apa yang dijamin dan apa yang TIDAK
- **Dijamin**: (i) byte yang ditandatangani == byte yang disalin dari SATU fd (`input_sha256`); penukaran/symlink/FIFO/tautan keras `unsigned.apk` setelah titik buka tidak berpengaruh; (ii) yang diverifikasi == yang ditandatangani (folder privat); (iii) `ok:true` hanya bila `signed.apk` di `builds` yang dibaca ulang berhash sama dengan yang diverifikasi; nama keluaran yang ditanam penyerang membuat job GAGAL (`EEXIST`/`EISDIR`), tidak pernah menerbitkan atau mengikuti sasaran lain; (iv) kunci tidak berpindah (alat tetap hanya membaca `--ks-pass file:` dari `/run/secrets`).
- **Tidak dijamin (jujur)**: (a) runner bisa menghasilkan `unsigned.apk` APA SAJA — persetujuan terikat pada ISI pohon SUMBER (dasar + delta, hash diff §5.3), bukan keluaran kompilator; (b) runner yang terkompromi dapat mengubah `signed.apk` SETELAH diterbitkan (uid sama, `builds` rw). Perubahan itu tidak dapat membawa tanda tangan pemilik yang sah (v2/v3 mencakup seluruh berkas) dan TERDETEKSI oleh hash di DB — worker menghitung ulang hash saat mengganti nama (tahap 8). Deteksi ini DIBUKTIKAN, bukan hanya ditulis: `verify-build` langkah 7b membalik satu byte artefak lewat kontainer runner lalu `artifact-info` harus kode 3 `hash_tidak_cocok`. **Prasyarat tertulis Tahap 5**: unduh = salin-lalu-hash-lalu-bandingkan (dicatat di PRD 09 Bagian B dan di badan PR); 2b tidak menegakkannya karena tidak ada rute unduh. Tidak ada mekanisme lain di 2b yang mencegah penulisan runner setelah terbit (§13 R-1).

### 7.4 Alternatif yang ditolak (dan alasannya)
| Alternatif | Alasan ditolak |
|---|---|
| **Uid berbeda untuk signer** + izin folder | Berkas milik uid lain di volume yang dihapus web (uid 10001) mengulang **pelajaran 3** (hapus-analisis dan prune gagal EACCES), menambah kerumitan setgid/umask/ACL yang TIDAK bisa dibuktikan di sandbox, dan tidak menutup (a): signer tetap membuka berkas runner lewat jalur. Kunci mode 644 di `secrets/` 700 (keputusan [A] 2a) tidak bergantung uid, jadi tidak ada keuntungan di sisi kunci |
| **`builds` read-only untuk signer + volume terbit `artifacts`** yang tak terpasang di runner | Paling kuat (menutup R-1b: artefak tak pernah ada di jangkauan runner), tetapi: bertentangan dengan matriks mengikat brief ("signer: builds + signwork + keystore"), menambah volume dan pemasang (web, worker), dan mengubah semua pembaca artefak (`signcheck`, Tahap 5). Manfaat tambahannya (cegah vs deteksi) dapat diambil Tahap 5 tanpa mengubah protokol; dicatat sebagai peningkatan pertama bila R-1 tidak dapat diterima |
| **Hanya baca-sekali, tanpa `signwork`** (alat dipanggil dengan `/proc/self/fd/N`) | Masukan terkunci ke inode, tetapi keluaran (`.sign-aligned.tmp`, `.sign-signed.tmp`) tetap di folder runner-writable: celah (b) tetap terbuka. Juga bergantung `/proc` dan perilaku zipalign/JVM terhadap `/proc/self/fd` yang tidak teruji |
| **Worker menyalin `unsigned.apk` ke `signspool`** | Memindahkan hingga 1 GiB lewat antrean berkas yang dirancang untuk JSON kecil; menambah penulis ke `signspool` dan satu salinan lagi; tidak menyelesaikan keluaran |
| **Hash di request sign** (worker meneruskan `output_sha256` runner ke signer) | Hanya mengikat ke klaim runner sendiri; signer tetap perlu menyalin untuk menutup (a). Rantai hash pada HASIL (`input_sha256`) memberi manfaat yang sama (deteksi tukar di antara runner selesai dan signer mulai, D3) tanpa mengubah format request 2a |
| `chattr +i`/`fs-verity`/seccomp | butuh capability atau kernel/filesystem yang tak tersedia dan tak boleh ditambah (cap_drop ALL) |

### 7.5 Bukti: tes balapan nyata (`tests/test_signer_race.py`)
Daemon NYATA (`_process` dimuat lewat `SourceFileLoader`, dijalankan sebagai fungsi atau subproses) dengan `zipalign`/`apksigner` PALSU di `PATH` yang berhenti di GERBANG berkas (`started.<alat>` ditulis, menunggu `go.<alat>`), sehingga "runner" (utas uji) bertindak tepat pada jendela:
| Skenario (di jendela) | Hasil wajib |
|---|---|
| saat `zipalign` menahan: `unsigned.apk` → ganti isi/`rename` lain/symlink ke `/etc/passwd`/FIFO/tautan keras | `ok:true` dengan `output_sha256` yang diturunkan dari byte ASLI (penanda isi asli ada, penanda isi jahat tidak ada); `input_sha256 == sha256(asli)` |
| saat `apksigner verify` menahan: buat `.sign-signed.tmp` sebagai berkas biasa/FIFO/symlink/direktori | `ok:false`, TIDAK ada `signed.apk` berisi isi penyerang; FIFO tidak menggantung (`within(10)`) |
| saat `apksigner verify` menahan: buat `signed.apk` sebagai direktori berisi / FIFO | `ok:false` (replace gagal) atau `signed.apk` sah; tak pernah isi penyerang |
| tukar `signed.apk` TEPAT setelah `os.replace` (hook `os.replace` yang dibungkus tes) | `ok:false`, `signed.apk` dihapus |
| `unsigned.apk` tumbuh tak terbatas saat disalin | `input_too_large`, `signwork` bersih |
| runner mengganti `builds/<aid>` dengan symlink ke direktori lain (mis. `work`), atau me-`rename` `builds/<aid>/<bid>`, SEBELUM signer membuka | signer: `input_unsafe`/`input_missing` (gagal-tertutup); sasaran symlink tidak disentuh |
| runner me-`rename` `builds/<aid>/<bid>` ke tempat lain / menaruh direktori berbeda bernama sama SETELAH signer membuka rantainya | signer menerbitkan ke inode yang ia buka; worker (membuka rantai BARU, tahap 8) mendapat berkas hilang/hash beda → `artifact_changed`; tidak ada `done` |
| sama seperti baris 1 dengan alat NYATA (`SIGNER_TEST_*` terisi; skip bersih di CI) | hasil sama; `apksigner verify` independen lulus |
Mutasi (§12.2): bukan-salin (alat membaca jalur builds), hapus `O_NOFOLLOW`/`nlink`, terbit tanpa `O_EXCL`, hapus baca-ulang, hapus `input_sha256` → masing-masing HARUS ditangkap tes ini. Tes balapan sisi worker/web/prune ada di §7.7 (`test_build_fs_chain.py`, `test_worker_builds.py`).

### 7.6 Temuan non-blocking 2a yang diselesaikan di bagian ini
(1) `error_text` keystore: `JobError(f"keystore_{state}", scrub(key.detail) or ERROR_TEXT[...])` — jalur `/run/secrets/...` disamarkan, uid/mode dan petunjuk perbaikan (`make keystore-access`) tetap; detail di `signer.hb` memakai teks tersaring yang sama. (2) sandi di argv `grep` skrip host: `signer-verify.sh` langkah 18 memakai `grep -F -q -f <(printf '%s\n' "$pw")` (pola dari berkas/fd, tidak di argv; `printf` builtin); syarat `${#pw} >= 16` dan `pw=""` sesudahnya dipertahankan. (3) tes signcheck FIFO tanpa batas waktu: semua tes FIFO/symlink di `test_signcheck.py` dibungkus `within(5)` (utas + `join`), gagal bila menggantung; helper `within` dipindah ke `tests/conftest.py`. Tes teks `test_signer_verify_script` diperbarui (bentuk baru `-f <(`; larangan `-e "$pw"`).

### 7.7 Konsumen `builds/` lain (worker, web, runner): rantai-dirfd bersama (review F-03)

Runner kini menulis akar `builds` (uid sama). Setiap komponen yang memakai `builds/<aid>[/<bid>]` lewat jalur string (`Layout.build_dir` + `Path.mkdir`/`safe_rmtree`/`rename`) bisa diarahkan penyerang: runner mengganti `builds/<aid>` dengan symlink ke `/data/work` (atau `/data/db`, `/data/spool` — semuanya rw di worker), lalu prune/pembersihan worker menghapus atau menulis ke sasaran itu. `fsutil.safe_rmtree` hanya memeriksa komponen TERAKHIR; komponen perantara ikut diselesaikan, dan fungsi aman yang ada hanya ada di skrip signer (tidak bisa diimpor worker). Integritas tanda tangan tidak rusak oleh ini (signer nofollow, hash dicocokkan ulang), tetapi kerusakan data lintas-analisis lewat kode baru 2b tidak boleh terjadi. Keputusan:
- `rvcore/fsutil.py` bertambah dua fungsi (stdlib; satu-satunya jalan ke `builds/` bagi semua konsumen non-runner-tool):
  - `open_dir_chain(root, *names, create=False, mode=0o755) -> int`: membuka `root` lalu tiap `name` relatif `dir_fd` dengan `O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC`; `create=True` → `mkdir(name, mode, dir_fd=)` (abaikan `EEXIST`) sebelum membuka. Nama harus string bilangan bulat positif (tanpa `/`, `..`, kosong); selain itu `ValueError`. `OSError` naik apa adanya (`ELOOP`/`ENOTDIR` = komponen ditanam; `ENOENT` = tak ada).
  - `rmtree_at(dirfd, name) -> None`: menghapus entri `name` di bawah `dirfd` TANPA mengikuti symlink: `lstat(dir_fd=)`; bukan direktori (berkas, symlink, FIFO, soket) → `unlink(dir_fd=)`; direktori → buka `O_NOFOLLOW|O_DIRECTORY`, hapus isi secara ITERATIF (tumpukan eksplisit; pohon 5000 tingkat tidak memicu `RecursionError`), lalu `rmdir(dir_fd=)`. `EACCES` pada direktori yang terkonfirmasi `S_ISDIR` → buka `O_PATH|O_NOFOLLOW|O_DIRECTORY`, `chmod('/proc/self/fd/<n>', 0o700)`, coba sekali lagi (perbaikan izin tanpa mengikuti symlink; niat yang sama dengan `safe_rmtree._onexc`; DIUKUR di sandbox sebagai uid 10001 pada direktori mode 000). `FileNotFoundError` diabaikan.
- Pemakai wajib: worker — buat folder (tahap 3), pembersihan (`src/`, `unsigned.apk`, `.sign-*`), hash ulang + rename (tahap 8, rantai dibuka BARU), prune (`rmtree_at(open_dir_chain(builds, str(aid)), str(bid))`); web — `artifact_info` dan `_delete` (`rmtree_at(open_dir_chain(builds), str(aid))`); signer — `open_build_dir` (pembungkus); runner — pengecekan awal (§6.2). Komponen `<aid>` yang ternyata symlink: `open_dir_chain` gagal `ELOOP`; pemanggil menghapus entri itu dengan `rmtree_at` pada induknya (men-`unlink` symlink, sasarannya utuh) dan melanjutkan/gagal-tertutup sesuai konteks.
- **Sapu yatim DIHAPUS dari desain** (§8.7, F-11): tidak diminta brief dan berisiko — penghapus otomatis atas daftar direktori yang dapat ditulis runner adalah perkakas yang paling berbahaya bila salah. Yatim langka (hapus sebagian gagal) dicatat sebagai R-16.
- Yang TIDAK dijamin: runner tetap bisa menghapus/merusak isi `builds/` (volume itu memang rw baginya): artefak hilang → `artifact-info` melaporkan; ini sama kelasnya dengan R-1 (ketersediaan/deteksi, bukan integritas tanda tangan).
- Bukti: `tests/test_build_fs_chain.py` (helper murni: symlink di tiap komponen rantai, FIFO/soket sebagai entri, direktori mode 000 dan berkas 444 sebagai uid 10001 via `setpriv`, pohon 5000 tingkat) dan tes balapan sisi worker di `test_worker_builds.py` ("runner" mengganti `builds/<aid>` dengan symlink ke direktori berisi penanda sebelum tahap 3, sebelum tahap 8, sebelum prune, dan sebelum `_delete` → `work/<n>` dan sasaran symlink UTUH, hanya symlink yang hilang/gagal-tertutup), plus tes AST §3 butir 6. Mutasi: ganti `open_dir_chain` dengan `Path.mkdir`/`safe_rmtree` biasa → tertangkap (§12.2).

## 8. Worker: `tasks.run_build`, pembatalan, pemulihan, retensi

### 8.1 Berkas dan konfigurasi
- `services/worker/builds.py` (BARU, ditambahkan ke daftar `COPY` eksplisit `worker/Dockerfile` — jebakan lama; tes statis: setiap modul yang diimpor `tasks.py`/`worker.py`/`pipeline.py`/`builds.py` ada di `COPY`), `tasks.run_build(build_id)` memanggil `builds.run_build` (impor lambat seperti `run_analysis`).
- `BuildConfig.from_env`: `TIMEOUT_BUILD` (1800, klem 10..3600), `TIMEOUT_SIGN` (900, klem 10..3600; signer menjepit lagi ke `SIGN_TIMEOUT` miliknya sehingga nilai efektif = min keduanya), `RUNNER_PICKUP_TIMEOUT` (120, sudah dibaca pipeline), `BUILD_KEEP` (via `store.build_keep()`). Compose meneruskan `TIMEOUT_BUILD` dan `TIMEOUT_SIGN` ke `worker` DAN `web` (web hanya untuk `job_timeout` RQ = `TIMEOUT_BUILD + TIMEOUT_SIGN + 600`, dihitung `jobs.enqueue_build`); `.env.example` bertambah dua baris komentar.
- Validasi masukan `run_build(build_id)`: `type is int`, `0 < n ≤ 999_999_999` (D13); baris tidak ada → log WARNING + return. RQ mengirim argumen dari web (terpercaya) tetapi tetap divalidasi.

### 8.2 Pra-cek signer, klaim, dan pilihan perilaku bila signer mati — **DIPILIH: gagal cepat**
`signer_status(make_spool(layout.signspool))` dibaca sebelum `claim_build`. Tidak hidup (`hb` > 20 dtk/tak ada) atau `keystore.state != ok` → `fail_build(signer_unavailable, <pesan SignerUnavailable>)` langsung dari `queued`; tidak ada runner yang dipakai. Alasan (D5): (1) RQ worker satu proses, antrean dipakai bersama analisis — menunggu di dalam tugas menahan SEMUA pekerjaan; (2) tidak ada penjadwal ulang di stack (hanya `requeue_orphans` saat start) sehingga "tetap queued" membutuhkan mekanisme polling baru yang tak diminta; (3) pemilik langsung diberi tahu alasan dan perintah perbaikan (`make up`), sedangkan build `queued` diam akan tampak macet. Signer yang mati DI TENGAH build ditangkap di tahap 6 (`SignerUnavailable` → `signer_unavailable`; artefak runner dibuang). Biaya: persetujuan harus diulang (`request` baru) — diterima, murah, dan aman (persetujuan terikat hash, bukan token yang bisa dipakai ulang). Alternatif "tetap queued + loop tunggu terbatas" ditolak karena butir (1).

### 8.3 Tahap build, tunggu, dan verifikasi hasil
- Kirim: `Spool(layout.spool).submit({job_id: new_job_id(aid,"build"), stage:"build", analysis_id, build_id, diff_sha256 (dari baris DB), sha256 (dari analisis), timeout, created})`.
- Tunggu (fungsi baru `_wait_runner` di `builds.py`, pola `pipeline._wait_result` tanpa `LogTail`): poll 1 dtk; hasil dibaca dengan **`signkeys.read_small(results/<id>.json, 64 KiB)`** + `buildproto.parse_build_result` (runner memproses input hostile; hasil tidak boleh membuat worker OOM/menggantung); belum diambil dalam `RUNNER_PICKUP_TIMEOUT` → tarik (`withdraw`) → `runner_unavailable`; detak runner basi > 45 dtk setelah diambil → `runner_unavailable`; lewat `timeout + GRACE(60)` → minta batal, +60 → `timeout`. Pembatalan: `store.is_build_cancel_requested` tiap putaran → `spool.request_cancel(job_id)`.
- Pemetaan hasil runner → `fail_build(error_code)`: kode runner dipakai apa adanya (≤ 40 huruf kecil, lolos regex store); `error_text` = `ERROR_TEXT[kode]` + (untuk `build_failed`) baris galat tersaring; `stage_log` = ringkasan (durasi, ukuran, `peak_mem_mib`, ekor log ≤ 1500).
- **Verifikasi hasil signer** (`builds._check_sign_result`), semuanya WAJIB: `res["ok"] is True`; `res["cert_sha256"] == owner` dengan `owner` = `signer_status().keystore.cert_sha256` yang dibaca SEKARANG (bukan di awal; kunci diganti di tengah → beda → `sign_cert_mismatch`); `verify.v2 and verify.v3`; `signer_count == 1`; `res["input_sha256"] == runner.output_sha256` (D3) dan `res["output_size"] > 0`. Satu syarat gagal → `fail_build` (`sign_cert_mismatch`, `artifact_changed`, atau `sign_bad_result`) dan `signed.apk` dihapus.
- Pembatalan saat `signing`: utas pemantau (koneksi DB sendiri, 1 dtk) men-set `threading.Event` yang diberikan ke `submit_and_wait(cancel=…)`; hasil `cancelled` → `cancel_build`.

### 8.4 Penamaan, `finish_build`, dan bila `finish` kalah dari pembatalan
`finish_build` hanya setelah tahap 8 §2.1. `BuildStateError` dari `finish_build`/`mark_signing` karena `cancel_requested` → worker menghapus artefak yang sudah dinamai dan memanggil `cancel_build` (pembatalan menang, konsisten dengan CAS `cancel_requested = 0`). Bila `cancel_build` SENDIRI melempar `BuildStateError` (baris sudah `failed` oleh `recover_stuck_builds` pada worker yang baru restart, atau final lain): tangkap, log WARNING, artefak tetap dihapus, return — tidak ada pengecualian yang lolos ke RQ. `output_format = 'apk'`: 2b hanya mendukung APK biasa; `request_build` menolak analisis yang `options.bundle` berisi (XAPK/APKS = Tahap 3) dengan `kode=paket_belum_didukung`.

### 8.5 Nama artefak turunan sistem
`output_name = f"{base}-modified-{build_id}.apk"`, `base` = `apk.package` (sudah dari manifes) bila ada, kalau tidak stem `filename_display`, kalau tidak `app`; disanitasi `re.sub(r"[^A-Za-z0-9._-]", "_", s)`, buang awalan `.`/`-`, dipadatkan, dipotong 80 karakter, harus lolos `_OUTPUT_NAME_RE` store (`[A-Za-z0-9][A-Za-z0-9._-]{0,119}`), fallback `app`. TIDAK dari catatan/`note`/AI/`requested_by`. Rename dengan `os.rename(…, src_dir_fd=bfd, dst_dir_fd=bfd)` (`bfd` = rantai §7.7 yang dibuka BARU di tahap 8); tujuan sudah ada → `os.replace` (nama mengandung `build_id` unik, jadi hanya sisa uji).

### 8.6 Retensi `BUILD_KEEP` dan prune (aman terhadap build aktif)
Setelah setiap build mencapai status final oleh worker (`done`, `failed`, `cancelled`) — dan di `finally` sebagai jaring — `builds.prune_analysis(conn, layout, aid, keep=None)`: `ids = store.prune_builds(conn, aid, keep)` (store sudah TIDAK PERNAH menyebut build aktif dan memisahkan kelompok `done` vs gagal/batal); untuk tiap id: **hapus direktori DULU** (`rmtree_at(afd, str(id))` dengan `afd = open_dir_chain(builds, str(aid))`, §7.7; `afd` gagal dibuka karena `<aid>` ditanam symlink → entri itu di-`unlink` lewat `rmtree_at(open_dir_chain(builds), str(aid))` dan baris-barisnya dihapus), baru `store.delete_build(conn, id)` (menolak non-final: `rowcount` 0). Direktori gagal dihapus (`OSError`) → baris TIDAK dihapus, WARNING, dicoba lagi pada prune berikut (tidak ada yatim DB↔disk yang tak terlacak). Pembungkus `builds.prune_for(aid)` (membuka koneksi sendiri, mencetak `pruned=<id,…>`) dipakai `verify-build` langkah 11 lewat kontainer sekali pakai dengan `BUILD_KEEP=2`. Prune dijalankan HANYA oleh worker (dan pembungkus uji itu) (penulis tunggal; tidak berlomba dengan web `delete`, yang menolak analisis dengan build aktif). Build `rejected` tidak punya direktori (rmtree no-op).

### 8.7 Pemulihan setelah restart (`worker.main`)
Urutan: `migrate` → `pipeline.reconcile()` (analisis; sudah membatalkan job runner yang berjalan dan MENGHAPUS semua `requests/*.json`, termasuk build yang belum diambil) → **`builds.reconcile(layout)`** → `requeue_orphans` (analisis) → **`builds.requeue_orphans(redis)`**.
- `builds.reconcile`: `store.recover_stuck_builds` (`building|signing` → `failed/interrupted`); untuk id itu hapus `src/`, `unsigned.apk`, `signed.apk`, `.sign-*` lewat §7.7 (idempoten; runner/signer yang masih menyelesaikan job yatim akan gagal sendiri atau meninggalkan sisa yang ikut dihapus prune). **Tidak ada sapu yatim** (F-11/§7.7): hapus-analisis yang gagal sebagian meninggalkan folder tanpa baris DB (R-16), dibersihkan pemilik lewat kontainer web (uid 10001), tidak otomatis.
- `builds.requeue_orphans`: build `queued` (dan `approved`) tanpa job RQ berawalan `build-<id>-` di antrean → `approved` dulu `queue_build`, lalu `enqueue` (`job_id=build-<id>-<hex8>`, `job_timeout` sama dengan web). Duplikat aman (CAS klaim). Konsekuensi yang disengaja: build yang ditahan `--hold` ikut dilepas bila worker restart.
- Kegagalan Redis saat start: `requeue_orphans` dibungkus sehingga worker tetap naik (Redis dicek `ping` di `main` sebelumnya); galat → log WARNING, build tetap `queued` dan dipulihkan pada start/`approve` berikutnya.

### 8.8 NB-2: analisis ulang dan hapus saat ada build aktif
Pemilik invarian = **store** (satu transaksi `BEGIN IMMEDIATE` dengan pembaruan analisis, jadi tak ada balapan dengan `create_build`): `reset_for_retry` (kedua cabang, termasuk `only_stage='analyzing'`) dan `delete_apk` mengembalikan `False`/`None` bila ada baris `build` berstatus `BUILD_ACTIVE` (termasuk `awaiting_approval`) untuk analisis itu; rute lama menerjemahkannya menjadi notice `busy` (rute tidak diubah selain `_delete`). Alasan sampai `awaiting_approval`: hash yang disetujui terikat pada baseline `work/<id>/apktool` yang akan dihapus analisis ulang. `routes_apk._delete` (±960-980) diperbarui: setelah `work` dan `files`, hapus **`builds/<id>`** (`rmtree_at(open_dir_chain(layout.builds), str(id))`, §7.7) dan bench seperti sekarang (`safe_rmtree`; runner hanya `bench:ro`, jadi tak ada penulis tak tepercaya atas induknya), masing-masing di `try/except OSError` + `log.exception` (satu kegagalan tak menggagalkan yang lain; sisa yatim: R-16). Aman terhadap uid 10001: web, runner, signer, worker, bench semuanya uid 10001; `copy_tree_safe` membuat mode 0644/0755 dan `safe_rmtree` memperbaiki izin direktori dan mencoba lagi; tidak ada langkah yang butuh root host (tes: pohon `builds/<id>` berisi direktori mode 000 dan berkas 444 dihapus oleh proses uid 10001 via `setpriv`).

### 8.9 Detak signer ke Redis (D7)
`worker.heartbeat_loop` menambah satu `SET signer:heartbeat` (TTL 30) dari `signspool.signer_status`: `{"ts": …, "state": …, "keystore_state": …, "cert_sha256": …}` (hanya bila `hidup`); web membacanya dengan validasi ketat (hex64, daftar state) untuk `status`. Gagal baca → tidak menulis; `status` melaporkan "signer: tidak diketahui".

### 9.2 Persetujuan: terikat hash, idempoten, dan tidak bisa dilakukan AI
- `approve_build`: `store.approve_build(conn, id, diff_sha256=H, statement_sha256=store.approval_statement_sha256(v), statement_version=v, via=via)` — **`store.approve_build` bertambah parameter `via: str = "ui"`** yang masuk ke detail audit `build_approved` (nilai `ui|cli`, divalidasi daftar tetap); hash tetap ikut klausa `WHERE` CAS (tidak ada celah cek-lalu-ubah). Pernyataan wewenang = konstanta store (`APPROVAL_STATEMENTS[1]`); CLI mencetaknya (`pernyataan=…`) sehingga tercatat di keluaran.
- Lalu `store.queue_build` → `jobs.enqueue_build(redis, id, job_timeout)` (`job_id=build-<id>-<hex8>`, `result_ttl=300`, `failure_ttl=86400`, pola `enqueue_analysis`). `RedisError` ditangkap: build tetap `queued` tanpa job (D10), `approve_build` mengembalikan `enqueued=False` + `galat` (CLI: kode keluar 3, status tetap tercatat).
- **Idempoten**: `approve` pada build `approved|queued` dengan `diff_sha256` yang SAMA (`hmac.compare_digest`) tidak mengubah persetujuan; ia memastikan `queued` dan memastikan ada job RQ (cek `job_ids` berawalan `build-<id>-`). Hash lain → `diff_berubah`; status lain (`building`, `done`, …) → `status_salah`. Inilah jalan "lepas tahan" dan jalan pulih dari Redis mati — tanpa perintah baru.
- **`--hold`** (penahan uji, D6): `approve --hold` = persetujuan + `queue_build` TANPA `enqueue`. Aman: tidak ada yang berjalan; terjangkau hanya dari shell VPS (CLI); dapat dibatalkan (`cancel`: `queued → cancelled`). Dipakai verify-build untuk negatif TOCTOU dan pembatalan `queued`, bukan `sleep`.
- **AI tidak bisa menyetujui**: (1) tidak ada tool AI baru — `ai/tools.TOOLS` tidak berubah (tes: himpunan kunci persis sama, tak ada nama mengandung `approve|build|sign`, tak ada impor `app.builds`/`buildctl` di bawah `app/ai/`); (2) tidak ada rute web baru (tes: himpunan rute tak berubah, tak ada impor `builds` di modul rute selain `routes_apk` yang dipakai `buildctl` — dan itu satu arah, `routes_apk` tidak mengimpor `builds`); (3) `buildctl` hanya berjalan di kontainer web lewat `docker compose exec` oleh pengguna shell VPS; kontainer `bench` (tempat perintah AI berjalan) tidak punya DB, Redis, maupun Docker socket; (4) satu-satunya jalan ke `approved` adalah `store.approve_build` yang menuntut `diff_sha256` = nilai tercatat; (5) keluaran CLI menyaring nama berkas buatan AI (tidak bisa memalsukan baris `kunci=nilai`, mis. `persetujuan=…`).

### 9.3 `python -m app.buildctl <perintah>` — format dan kode keluar
- **Keluaran** hanya baris `kunci=nilai` (kunci `[a-z_0-9.]+`, nilai satu baris, karakter cetak saja, ≤ 500; kontrol/pengendali arah → spasi). Teks bebas bergaris banyak diawali penanda 3 karakter yang tidak mungkin berupa `kunci=`: `o| ` (stdout shell), `e| ` (stderr), `l| ` (log/stage_log). Skrip bash hanya memakai `sed -n 's/^kunci=//p'`; tidak ada JSON.
- **Kode keluar**: `0` harapan terpenuhi; `3` harapan TIDAK terpenuhi atau galat operasional (selalu mencetak `kode=<stabil>` dan `alasan=<teks>` atau `galat=<teks>`); `64` salah pakai (argparse dibelokkan: pesan ke stderr). Pengecualian tak terduga dibungkus → `kode=internal galat=<NamaGalat>` kode 3 (tidak ada traceback di stdout, tidak ada kode 1/2).
- **Validasi argumen**: id = bilangan bulat `1 ≤ n ≤ 999_999_999` (di luar itu → 64; D13); `--diff-sha256` = `[0-9a-f]{64}`; `--timeout` int 1..86400 (bawaan: `analyze` 900, `wait` 1800, `shell` 60); `analyze -` (stdin) atau `analyze <path>` (berkas biasa yang dapat dibaca, bukan direktori): ukuran ≤ `MAX_UPLOAD_MB`; `shell`: perintah tidak kosong, ≤ `MAX_COMMAND_CHARS`, tanpa NUL.

| Perintah | Kunci keluaran utama | Kode 3 bila |
|---|---|---|
| `analyze (- \| <path>) [--timeout S] [--uniq] [--no-wait]` | `duplicate`, `apk_id`, `analysis_id`, `sha256`, `status`, `elapsed` | ditolak validasi (`kode=<kode ApkRejected>`; stdin melebihi batas → `terlalu_besar`), Redis mati (`antrean_mati`; analisis ditandai gagal seperti rute), status akhir ≠ `done`, waktu habis |

`analyze -` (F-04): kontainer web TIDAK memasang repositori/`testdata` (rootfs ro, `testdata/` gitignored), jadi APK dialirkan lewat stdin dari host (`docker compose exec -T web python -m app.buildctl analyze - --uniq < testdata/vulnsample.apk`, pola `run_sc_in put … <"$APK"` di `signer-verify.sh`). stdin dibaca per blok 1 MiB ke `uploads_tmp/<uuid>.part` sambil menghitung sha256/md5/ukuran; melewati `settings.max_upload_bytes` → berhenti, `.part` dihapus, `kode=terlalu_besar`. `--uniq` menambah entri ZIP acak `assets/uniq-<hex>.txt` ke `.part` (`zipfile` mode `a`, di disk, bukan memori) lalu menghitung ulang hash, sehingga sha256 unik per run (D8). Sesudahnya SAMA dengan rute upload: `apkcheck.validate_apk(path, routes_apk._limits())`, `routes_apk._store_upload(received, name, options, "cli")` (dedup + audit `upload` dengan `ip="cli"`), `jobs.enqueue_analysis`. `analyze <path>` membuka berkas itu dan memakai jalur yang sama (pemakaian manual di dalam kontainer; `verify-build` TIDAK bergantung padanya). Impor privat `_store_upload`/`_limits` dari `routes_apk` dijaga tes (nama berubah = tes gagal).
`shell` (F-05): `shellspool.run_command(make_spool(layout.root / "benchspool"), aid, command, timeout=T, sha256=None)` LANGSUNG (jalur spool = `Layout.root/benchspool` = `/data/benchspool`, titik pasang compose yang sama dengan bawaan `AI_SHELL_SPOOL`; CLI tidak membaca `ai.config`). CLI tidak pernah mengimpor `ai.tools` (tes AST) dan berjalan dengan `AI_SHELL_ENABLED=0` (tes menyetel env itu ke `0` dan mengharapkan `status=ok`); keluaran disaring pembersih CLI. Tanpa audit tambahan: itu perintah pemilik sendiri (audit `ai_shell_run` ada untuk AI yang tak tepercaya); persetujuannya yang diaudit (`via=cli`).
`wait` dan `status` memakai koneksi DB sendiri (tanpa Redis kecuali membaca antrean untuk alasan). `delete` (F-06): `SELECT apk_id FROM analysis WHERE id = ?` (tak ada → `kode=analisis_tidak_ada`) lalu `routes_apk._delete(apk_id, "cli")` (jalur yang sama dengan UI; yang dihapus adalah APK beserta SEMUA analisisnya — `verify-build` memakai APK unik) dan memeriksa `os.path.lexists` untuk `builds/<aid>`, `bench/<aid>`, `work/<aid>`. `busy` selama ada build aktif (NB-2), karena itu pembersihan skrip selalu `cancel` + `wait` dulu (§10).

### 9.4 Alasan pada `status` (kunci `alasan=`)
| Status | Alasan |
|---|---|
| `awaiting_approval` | "menunggu persetujuan: jalankan approve --diff-sha256 <hash>" |
| `queued` | job RQ ada → "antre di worker: N pekerjaan di depan; runner <idle\|sibuk (job …)\|MATI>; signer <hidup\|MATI: build akan gagal signer_unavailable>"; tidak ada job → "queued tanpa job di antrean (ditahan --hold atau Redis gagal saat disetujui): jalankan approve lagi dengan hash yang sama" |
| `building` | runner sibuk dengan job build-nya + lama berjalan; atau "detak runner hilang" |
| `signing` | detak signer (`busy`/`idle`) + lama |
| `done` | nama artefak + ukuran |
| `failed`/`cancelled` | `error_code` + `error_text` + petunjuk (mis. `signer_unavailable` → "make up") |
Sumber keadaan runner/signer: Redis `runner:heartbeat` dan `signer:heartbeat` (D7); Redis mati → "antrean/detak tidak terjangkau" tanpa menggagalkan `status`.

Validasi masukan eksternal ringkas (lokasi pemilik): request `init/diff` → bench (§4.2); request `build` → runner (§6.1); request `sign` → signer (`signspool.validate_request`, ketat dari 2a); hasil runner/bench/signer → worker/web dinormalkan, ukuran dibatasi SEBELUM dibaca (64 KiB runner/signer, 1 MB bench), tidak pernah diteruskan mentah; argumen CLI (§9.3); `RQ` argumen `build_id` (§8.1). Kepemilikan invarian: **hash ↔ pohon yang dibangun = runner** (satu-satunya yang membaca pohon); **tidak ada `approved` tanpa hash = store** (CAS); **ok:true == berkas terverifikasi = signer**; **kuota ruang kerja = bench**; **tidak ada analisis ulang/hapus saat build aktif = store**; **tidak ada penulis AI = tidak adanya jalur** (bench tanpa builds/DB/Redis; web tanpa tool).

### 11.1 Kasus tepi yang ditangani (masing-masing punya tes)
- `project` diganti AI menjadi symlink/berkas: `init` tanpa `force` = `exists` (tak diikuti); `force` menghapus tautannya, bukan sasarannya; runner/diff membuka `project` dengan `O_NOFOLLOW` → `no_workspace`/`belum_init`.
- AI menghapus `AndroidManifest.xml`/`apktool.yml`: diff memuatnya sebagai `R`; build gagal di apktool (`build_failed`) dengan log; bukan kasus khusus.
- Berkas mode 000 / direktori tanpa izin baca di `project` (milik uid yang sama tetapi tak terbaca): `tree_unreadable` dengan path proyek relatif (gagal-tertutup), bukan dilewati.
- Nama sangat panjang, Unicode (NFC≠NFD), `A.txt`/`a.txt`, nama dengan `\n`/pengendali arah: hash deterministik; keluaran CLI disaring.
- `.last-used` dan berkas lain di `$WS` di luar `project/`: tidak ikut diff/snapshot.
- Build kedua untuk analisis yang sama saat satu build aktif: `build_aktif` (indeks unik parsial); `approve` dua kali: idempoten; dua job RQ untuk satu build: yang kedua kalah CAS dan keluar.
- Signer dimulai ulang antara pra-cek dan tahap tanda tangan: `SignerUnavailable` → `signer_unavailable`; signer dimulai ulang di tengah job → `aborted` dari `abort_orphans` → `sign_aborted`.
- Folder build sudah ada dengan sisa (worker restart; sisa uji): dihapus lewat `rmtree_at` (§7.7) lalu dibuat ulang di tahap 3. `unsigned.apk` hasil runner pada jalur GAGAL/batal dihapus (tidak menunggu prune; bisa ±1 GiB).
- Hasil runner/signer berupa FIFO/symlink/10 MiB: `read_small` → `bad_result` tanpa menggantung (tes `within`).
- Analisis bundel (XAPK/APKS): `paket_belum_didukung`. Analisis `done` tetapi apktool gagal (`warn`/`failed`): `create_build` menolak (`apktool_tidak_ada`).
- `BUILD_KEEP` di luar 1..100 atau bukan angka: `store.build_keep()` menjepit/bawaan (sudah teruji Tahap 1).

### 12.4 Rencana bukti sandbox (WAJIB; keluaran ditampilkan di laporan akhir)
Harness `scripts`-luar-repo (di `/projects/sandbox/emu-2b/`, tidak di-commit) menjalankan DAEMON NYATA sebagai proses terpisah dengan `DATA_DIR` sementara, memakai `setpriv --reuid=10001 --regid=10001 --clear-groups`:
- **bench-daemon** (op `init`/`diff`/`run`; Landlock ABI v2 di sandbox bila dapat dipasang; bila tidak, dicatat dan perintah `run` ditolak — op `init`/`diff` tetap dibuktikan karena tak terkurung); **runner-daemon** (apktool 3.0.3 NYATA + aapt2 + wrapper produksi dengan `AAPT2_EXEC_DIR` = tmpfs `exec` buatan, `/tmp` tmpfs `noexec`); **signer-daemon** (Build-Tools 37 NYATA + keystore sementara `keytool` lokal, kunci milik uid lain mode 644 di folder 700 — pola 2a); **worker** = `tasks.run_build` dipanggil oleh "shim" polling (TIDAK ada Redis/RQ di sandbox: shim menggantikan RQ dan sekaligus menjalankan jalur `requeue_orphans`; `jobs.enqueue_build` diuji terpisah dengan `rq.Queue` palsu); **web/buildctl** = `python -m app.buildctl` sungguhan terhadap DB sementara (Redis menolak koneksi → jalur "Redis mati" ikut teruji nyata).
- **Tampilan mount per layanan** (`unshare -m` + `mount --bind`; folder "view" terpisah per layanan): runner mendapat `bench` `ro` (remount `ro,bind`), `builds` rw, tanpa `signspool/signwork/benchspool/files/db`; bench tanpa `builds`; signer dengan `builds`+`signspool`+`signwork`; worker tanpa `signwork`/`bench`. Bukti: percobaan tulis ke bind `ro` → `EROFS`; `ls` volume terlarang → tidak ada. Berkas milik root/uid lain mode 600/644 dalam folder 700; bind per-berkas untuk kunci; tmpfs `noexec` untuk `/tmp` dan `exec` untuk `/opt/aapt-exec` milik 10001; penghapusan `builds/<id>` oleh uid 10001.
- **Skenario `verify-build.sh` versi tanpa Docker**: shim `docker` yang menerjemahkan `docker compose exec/run … <svc> <cmd>` menjadi pemanggilan langsung (dalam tampilan mount layanan itu) sehingga SELURUH langkah 1–13 berjalan, termasuk negatif TOCTOU (`--hold`) dan balapan signer (§7.5, alat nyata). Keluaran: tabel lengkap + kode keluar.
- **Celah emulasi (DITULIS di laporan)**: JDK 21/25 mise bukan image `openjdk-21-jre-headless` Debian; tidak ada cgroup (`mem_limit`, `pids_limit`, `memory.peak` → `peak_mem_mib` null), tidak ada seccomp/AppArmor, tidak ada `cap_drop`/`no-new-privileges` yang nyata, rootfs read-only hanya sebagian (jalur kerja dibuat `ro` lewat bind, bukan seluruh `/`), Landlock ABI v2 (bukan v4 VPS; jaringan tidak dikunci), bukan jaringan Docker, tanpa Redis/RQ (shim), tanpa `tmpfs` Docker sungguhan (`mount -t tmpfs` buatan), uid host `deploy` ≠ 1000 mungkin; Python venv 3.12 (`/projects/sandbox/.venv-t2b`), sistem 3.11 memberi kegagalan tak terkait; `docker compose config` tidak bisa dijalankan (conmon hilang).
- **DIBUKTIKAN vs BELUM DIUJI** akan ditulis eksplisit di laporan dan badan PR; **BELUM DIUJI (butuh Docker VPS)** dengan perintah persis, hasil yang diharapkan, dan gejala: `git pull --ff-only` · `docker compose version` · `docker compose config -q` · `COMPOSE_FILE=docker-compose.yml:docker-compose.keystore.yml docker compose config -q` · `docker compose --profile build build` · `make up` · `make runner-selftest` · `make signer-selftest` · `make bench-selftest` · `make signer-verify` · `make verify-build`. Gejala yang diantisipasi (tabel di `docs/deploy.md` dan PR): bind `bench:ro` ke runner (`EROFS`/`Permission denied` saat menyalin → volume `bench` baru dari image tanpa `/data/bench`), izin volume `builds`/`signwork` baru (dimiliki root bila mount point tak ada di image → `mkdir -p … && chown 10001` di Dockerfile), `workspace_changed` palsu (pohon hidup berubah oleh proses latar AI, atau `AI` sedang menulis; ajukan ulang), runner terkunci di belakang analisis panjang (`queued` lama), tmpfs `/opt/aapt-exec` 16m penuh, `/tmp` 256m penuh pada APK besar (build gagal dengan `No space left`), `mem_limit` runner 3g dengan `-Xmx2g` + aapt2 untuk APK besar, `signwork` kurang disk (`no_space`), `docker compose exec -T web` tanpa TTY (`-T` sudah dipakai).

**A-01 (F-01, MEDIUM) — `base` ditaruh TERAKHIR di payload `diff_sha256`.**
- Keputusan: ubah D11/§5.3/§6.2.4. Payload byte persis `b'{"v":2,"e":[' + b','.join(entri_json) + b'],"base":"' + base_hex.encode() + b'"}'`; `entri_json` = `json.dumps(entri, separators=(",",":"), ensure_ascii=True)` per entri. Dihitung streaming satu lintasan: potongan di-`update` ke SHA-256 saat entri keluar, `base` (SHA-256 aliran dasar yang sama yang dibaca penggabung) ditambahkan paling akhir. DILARANG: dua lintasan atas dasar, menahan semua entri di memori, atau urutan kunci lain. Pilihan alternatif (`sha256(b"v2\n"+…)`) TIDAK dipakai.
